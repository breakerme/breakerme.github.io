AI学习之-哈希表

# 哈希表 (Hash Table)

哈希表是一种通过"键"直接定位到"值"的数据结构，查找速度极快（平均 O(1)）。

# 核心思想

键 (Key)  →  哈希函数  →  下标 (Index)  →  直接取值
 "apple"  →  hash()   →      3        →  array[3]
1
2

用一个函数把键转换成数组下标，从而直接跳到存储位置，而不用逐个查找。

# 直观比喻

想象一个图书馆的存包柜：

  • 你的名字（键）经过某种规则 → 分配到 37 号柜（下标）
  • 下次取包时，直接去 37 号，不用逐个柜子找

# 哈希冲突

两个不同的键算出了相同的下标，称为冲突：

"abc"  →  hash()  →  5  ← 冲突！
"xyz"  →  hash()  →  5  ←
1
2

解决方法：

│ 冲突的位置挂链表   │ 冲突时往后找下一个空槽                  │
│                 │                                      │
│ index 5 → [abc] │ index 5: abc                         │
│           [xyz] │ index 6: xyz  ← 顺移一格              │

# 与其他结构的速度对比

操作 数组 链表 二叉搜索树 哈希表
查找 O(n) O(n) O(log n) O(1)
插入 O(n) O(1) O(log n) O(1)
删除 O(n) O(n) O(log n) O(1)

# 回到两数之和

// 普通数组查找：要从头扫到尾 → O(n)
for (int j = 0; j < n; j++) {
    if (nums[j] == complement) ...  // 最坏要找 n 次
}

// 哈希表查找：直接算出位置 → O(1)
hash = complement % tableSize;
if (keys[hash] == complement) ...   // 一步到位

# 为什么 tableSize = 8？

# 直接原因

int tableSize = numsSize * 2;
// numsSize = 4（数组有4个元素）
// tableSize = 4 × 2 = 8
1
2
3

# 但为什么要 ×2？—— 装载率

装载率 = 已存元素数 ÷ 表大小

tableSize = 4（不×2）：最坏情况存满4个元素
装载率 = 4/4 = 100%  ← 极易冲突！

tableSize = 8（×2）：最多存4个元素
装载率 = 4/8 = 50%   ← 冲突少，性能好
1
2
3
4
5

# 用图理解：停车场类比

装载率 100%（表大小=4）        装载率 50%（表大小=8）

┌────┬────┬────┬────┐         ┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 2  │ 7  │ 11 │ 15 │         │ 2  │    │ 7  │    │ 11 │    │ 15 │    │
└────┴────┴────┴────┘         └────┴────┴────┴────┴────┴────┴────┴────┘
  全满！新来的车没地停              半空！新来的车很容易找到位置
  → 大量冲突，性能退化为 O(n)      → 冲突少，保持 O(1)

# 装载率对性能的影响

装载率 平均查找次数 性能
50% 约 1.5 次 ✅ 很好
75% 约 2.5 次 ⚠️ 一般
90% 约 5.5 次 ❌ 较差
100% 可能无限循环 💀 崩溃

# 结论

tableSize = numsSize × 2
                  ↑
           保证装载率 ≤ 50%
           让哈希表始终保持高性能
1
2
3
4

×2 不是魔法数字，工程上通常保持装载率在 50%~75% 之间。 很多语言的内置哈希表（如 Java HashMap）默认在装载率超过 75% 时自动扩容。

# 哈希冲突的解决方法

# 方法一：链地址法（Chaining）

每个槽位挂一条链表，冲突的元素都加到链表里。

插入：2, 10, 18（tableSize=8，都映射到下标2）

hash(2)  = 2 % 8 = 2
hash(10) = 10 % 8 = 2  ← 冲突！
hash(18) = 18 % 8 = 2  ← 又冲突！

table:
下标0: 空
下标1: 空
下标2: [2] → [10] → [18]   ← 链表串起来
下标3: 空
...

// 伪代码
int hash = key % tableSize;
Node* node = table[hash];
while (node != NULL) {
    if (node->key == key) return node->value;  // 找到
    node = node->next;
}

# 方法二：开放寻址法（两数之和用的）

冲突时往后找空槽，所有元素都存在数组里。

# 线性探测

插入 2, 10（tableSize=8）

① 插入 2：hash = 2%8 = 2，table[2] 空 → 存入
② 插入 10：hash = 10%8 = 2，table[2] 有人！
           → 看 table[3]，空 → 存入

下标:  0    1    2    3    4    5    6    7
      [空] [空] [ 2] [10] [空] [空] [空] [空]
                  ↑    ↑
               原位  挪到这里

查找 10：
① hash = 10%8 = 2，table[2] = 2，不是10
② 往后一格，table[3] = 10 ✅ 找到！
1
2

# 二次探测（跳着找，减少聚集）

冲突时不是 +1 +1 +1 地找，而是 +1 +4 +9 地跳：

第1次冲突 → 跳 1² = 1 格
第2次冲突 → 跳 2² = 4 格
第3次冲突 → 跳 3² = 9 格

比线性探测更分散，减少"连续占用"问题

# 两种方法对比

链地址法                        开放寻址法
┌──────────────────────┐        ┌──────────────────────┐
│ table[2] → 2→10→18   │        │ table[2] = 2         │
│                      │        │ table[3] = 10        │
│ 元素存在链表节点里      │        │ table[4] = 18        │
│ 需要额外指针空间        │        │ 全部存在数组里         │
└──────────────────────┘        └──────────────────────┘

对比项 链地址法 开放寻址法
内存 需要额外指针 只用数组，更省
装载率 可以超过100% 必须 < 100%
缓存友好 ❌ 链表跳跃 ✅ 连续内存
删除操作 ✅ 简单 ⚠️ 需要墓碑标记
适合场景 数据量不确定 数据量可预估

# 根本解决之道：好的哈希函数

冲突再多，本质是哈希函数把太多键映射到同一位置。

坏的哈希函数：hash(key) = 0      → 全部冲突，退化成链表 O(n)
好的哈希函数：均匀分布到每个槽位  → 冲突极少，保持 O(1)
1
2

解决冲突是补救措施，设计好的哈希函数才是根本。

# Node 是什么

Node 是链表中的一个节点，可以理解为链条上的一个环。

# 现实类比

火车 🚂

[ 车厢1 ] → [ 车厢2 ] → [ 车厢3 ] → NULL
  data=2      data=10     data=18
  next=●      next=●      next=NULL
      │            │
      └──────►下一节车厢

每节车厢就是一个 Node，装着数据和指向下一节的指针。

# C语言中的 Node

typedef struct Node {
    int key;          // 存的键（比如 2、10、18）
    int value;        // 存的值（比如数组下标）
    struct Node* next; // 指向下一个Node的指针
} Node;

# 创建和连接 Node

// 创建三个节点
Node* a = malloc(sizeof(Node));  a->key = 2;
Node* b = malloc(sizeof(Node));  b->key = 10;
Node* c = malloc(sizeof(Node));  c->key = 18;

// 连接成链表
a->next = b;
b->next = c;
c->next = NULL;  // 最后一个指向NULL，表示结束
